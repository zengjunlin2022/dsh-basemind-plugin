## 4. Plan 偏差與決策（Ruling）

1. **不建立 git worktree、不 commit**：AGENTS.md 與計畫 §10.1 明定由使用者人工審查後手動 commit。成本：變更直接落在使用者的 `main` checkout。
2. **integration 不呼叫 `index_rescan {}`**：計畫 §5.5 原寫「以 `index_rescan` 觸發、再輪詢」，實測冷快取 rescan > 90 s，會直接 timeout。改為等 daemon 自行建置並輪詢 `index_status`。成本：若建置真的卡住，測試要 240 s 才失敗。
3. **`code_grep` 的 `structuredContent.hits` 是物件**（`{ "<path>": { "<symbol>": ["<line>: <text>"] } }`），不是陣列；斷言改為物件 + 序列化內容含命中字串。成本：形狀檢查比精確 schema 寬。
4. **測試時間預算上調**：`TEST_TIMEOUT_MS` 120 s → 300 s、新增 `INDEX_BUILD_TIMEOUT_MS` 240 s、`startSession` 的 `toolCallTimeoutMs` 90 s → 120 s（等於插件預設值）。成本：失敗案例較慢才回報。
5. **新增 `.github/workflows/compat.yml`**：計畫列為「建議新增」，已實作但未在 CI 執行過。成本：若 YAML 或 asset 名稱有誤，只會在 dispatch 時失敗。
6. **未改插件預設 `toolCallTimeoutMs`（120 s）**：依計畫 §8.5，量測未達 10k 檔案規模，不擅自改預設。成本：超大 repo 冷索引仍可能 timeout（見 §5）。
7. **未新增 `basemind scan`／自動建索引等啟動副作用**：維持 `autoProvision: false`。
8. **計畫 §8.5（fake server timeout／cancel 新案例）與 §8.6（worktree 隔離自動化案例）本輪未實作**：timeout／cancel 程式碼未改動，屬既有行為；worktree 隔離只在 review 前的真實 probe 觀察過，未寫成自動化測試。

## 5. 未驗證範圍與剩餘風險

- **DSH Desktop 實際載入（Phase 5 未執行）**：未在獨立 test profile 安裝 tarball、未在真實 session 呼叫工具、未驗證卸載後 relay 清理。需要使用者授權的測試 profile。
- **macOS／Linux 與 0.32 真實 binary**：0.33.0 已在 Windows 以 checksum 驗證的官方 asset 實跑 legacy smoke（1/1 pass，17.6 s）；0.32.0、macOS 與 Linux 仍未執行，`compat.yml`／`release.yml` 是補齊手段。
- **大型 repo（10k+ 檔案）冷索引**：未量測；本機小型 repo 已出現 106 s，插件預設 120 s 餘裕不大。若常態超過，依計畫只建議調整 `toolCallTimeoutMs`，不改預設。
- **升級窗口 `-32003 backend_unavailable`**：未模擬新舊 daemon 並存；錯誤訊息現在會帶 `[jsonrpc=-32003]`，但仍需文件引導使用者 `comms stop`。
- **npm launcher（`.cmd`）佈局**：本機為 GitHub Releases 的 `.exe`；`.cmd` 路徑只有既有單元測試覆蓋。
- **`basemind://outline/{path}` 的 `text/toon` 在 DSH UI 的呈現**：未在 Desktop 驗證。
- **CI 實跑**：`release.yml` 的新步驟與 `compat.yml` 從未在 GitHub Actions 執行過（本機僅做 YAML 解析）。

## 6. 後續（由使用者執行）

1. 人工審查本文件與 `git diff`（12 個修改檔 + 6 個新增檔 = 18）。**`package.json` 目前只在 worktree 是 0.2.0、index 仍是 0.1.6，必須 `git add package.json`**，否則 `v0.2.0` 的 tag/version 檢查會失敗（見 §7 C1）。
2. 手動 commit，建議訊息：`feat: 適配 BaseMind 0.34.0 並發布 0.2.0`。
3. 需要 OS 相容性證據時，手動 dispatch `BaseMind compatibility` workflow。
4. `git tag v0.2.0` 並 push 後，`release.yml` 會下載 0.34.0、以 `BASEMIND_REQUIRE_INTEGRATION=1` 跑真實 integration 再 publish。
5. 發布後提醒使用者：升級 BaseMind 需 `basemind comms stop` → `basemind scan` → 重開 session，且舊工具名稱已失效。
