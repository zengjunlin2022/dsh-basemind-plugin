## 0. 摘要

### 0.1 結論

**現有橋接架構可以承受 BaseMind 0.34.0 的工具重整，但契約資訊與測試、文件必須補齊。**

已用真實 0.34.0 二進位、隔離的 `BASEMIND_DATA_HOME` / `BASEMIND_COMMS_DIR` 與插件入口做過端到端驗證：

- 插件現行 `index.js` 在 0.34.0 上成功註冊 **18 個工具**（15 個 verb tools + 3 個 agent tools）、1 個 prompt section、1 個 resource provider，沒有 warning。
- 0.34.0 的 18 份 `inputSchema` 全部通過現有 normalizer 與 DSH schema 驗證；`properties`、`required`、`enum` 無損失，也沒有 `$ref` / `anyOf` / `allOf` / `oneOf` 需要降級。
- 0.34.0 的成功與失敗結果都帶 `structuredContent`，但 [lib/tool-bridge.js](../lib/tool-bridge.js) 目前只把 `text` / `content` / `isError` 放進 envelope，**`structuredContent` 被丟棄**；錯誤的 `error` / `retryable` 代碼也無法傳到 DSH。
- 0.34.0 的文字區塊不再全部是 JSON（`code_grep`、`code_outline`、`git_diff`、`find_files` 清單改為 TOON 或行導向文字）。插件只做文字投影，因此模型仍可讀；但不能再假設文字可被 `JSON.parse`。
- 現有 integration test 固定 0.29.3 的九個工具與 `mode` 呼叫，遇到 0.34.0 會失敗。本次實測 `npm test`：**149 tests、146 pass、3 fail**，3 個失敗全部來自 integration test 的舊假設。
- MCP Tasks 是伺服器端 **由 client capabilities 決定是否啟用** 的 SEP-2663 擴充；插件 initialize 送 `capabilities: {}`（[lib/stdio-client.js](../lib/stdio-client.js) 第 465 行），所以 0.34.0 一律回傳 inline 結果，**本次不需要實作 Tasks**。
- 0.34.0 的 tool rename（`code` / `git` / `memory` / `admin` → 15 個 verb tools）是上游破壞性變更，不是插件 bug；插件保持動態 discovery，不應硬編碼、也不應模擬舊工具。

### 0.2 必須修改（最小集合）

1. `lib/tool-bridge.js`：保留 `structuredContent`；把 `isError` 結果的 `{error, retryable}` 與 JSON-RPC error code 帶進錯誤訊息。
2. `fixtures/` 與 `test/`：新增 0.34.0 真實契約 fixture；更新 integration test；新增 0.34 專屬回歸與 legacy 動態 smoke。
3. `README.md`、`README.zh.md`、`CHANGELOG.md`、`AGENTS.md`：工具清單、resources、隔離語意、升級步驟與 envelope 契約。
4. `package.json`：版本 `0.1.6` → `0.2.0`（只改版本，不加依賴）。
5. `.github/workflows/`：讓 release 驗證不得因 integration skip 而假通過（見 §5.9）。

### 0.3 不需要修改

- `index.js`（動態 discovery / 註冊 / resources / prompt section 已相容）。
- `lib/schema.js`（0.34 schema 全數可表達，無降級）。
- `lib/result.js`（純文字與 TOON 都能投影）。
- `lib/mcp-session.js`（已經保留 `structuredContent`）。
- `lib/stdio-client.js`（tasks 不協商；cancel / timeout 既有行為仍適用）。
- `lib/workspace-pool.js`、`lib/executable.js`、`cordis.patch.yml`、`locale/`、`scripts/`。
- `lib/config.js`：程式不需要改；120 s 預設是否足夠，待大型 repo 量測後只做文件與設定建議。

### 0.4 最大風險

1. BaseMind 0.34 的 `RELEASE_MINOR 33 → 34` 會讓**每個 view 第一次開啟時重建索引**；使用者升級後第一次開啟大型 repo 可能很久。插件不應代為 scan，但要接受「空索引 / building_index」是正常的中間狀態。
2. 0.34 把 daemon socket / lock / comms store 移到 `comms/g1/`，並把 daemon protocol 從 4 升到 7；升級窗口內新舊 daemon 可能互斥，工具呼叫會收到 retryable 的 `backend_unavailable`（JSON-RPC `-32003`）。插件只需如實回報，不應自行殺 daemon。
3. 工具的「使用者可見名稱」從 9 個變成 15 個 verb + 3 個 agent tools；任何既有的 DSH 權限設定、prompt、腳本若寫死 `mcp__basemind__code` 等舊名就會失效。插件不修改 preset，但文件與 CHANGELOG 必須明示。
4. 真實 integration test 目前會因為 PATH 上沒有 `basemind` 而 skip；CI 沒有安裝 BaseMind，release workflow 的 `npm test` 也是 skip。這是**假通過**風險，必須以 `BASEMIND_REQUIRE_INTEGRATION=1` 與 release gate 修正。

## 2. 官方破壞性變更摘要（0.33 → 0.34）

### 2.1 MCP 工具重整（ADR-0018）

0.34.0 以「一個工具一件事」取代原本以 `mode` 分派的 `code`、`git`、`memory`、`admin`。**沒有 alias**；呼叫舊名稱會得到 JSON-RPC `-32602` / `tool not found`（本次真實採集已確認）。

| 舊工具 / mode | 新工具 |
|---|---|
| `code` `outline` | `code_outline {path}` |
| `code` `symbols` | `code_symbols {name}` |
| `code` `expand` | `code_read {path, symbol}` |
| `code` `grep` | `code_grep {pattern}`（預設 literal；regex 要 `regex: true`） |
| `code` `semantic` | `code_search {query}` |
| `code` `chunk` | `code_read {path, line, end_line}`（CLI 保留 `code chunk`） |
| `code` `references` | `code_refs {name}` |
| `code` `callers` | `code_refs {name, path}` |
| `code` `implementations` | `code_refs {name, relation: "implementations"}` |
| `code` `dependents` | `code_refs {name, relation: "importers"}` |
| `code` `definition` | `code_refs {name, relation: "definition", path, line}` |
| `code` `find` | `find_files {query}` |
| `code` `files` | `find_files {}` |
| `memory` `documents` | `docs_search {query}` |
| `memory` `put` | `memory_save {key, value}` |
| `memory` `get` / `list` / `search` | `memory_search {key}` / `{prefix}` / `{query}` |
| `memory` `delete` | CLI-only：`basemind memory delete <key>` |
| `git` `recent` / `touching` / `by_path` | `git_log {}` / `{path}` / `{path: "dir/"}` |
| `git` `search` / `show` / `symbol_history` | `git_log {query}` / `{author}` / `{rev}` / `{path, symbol}` |
| `git` `churn` | CLI-only：`basemind git churn` |
| `git` `blame` / `blame_symbol` | `git_blame {path, line, end_line}` / `{path, symbol}` |
| `git` `status` | `git_diff {}` |
| `git` `diff` / `diff_outline` | `git_diff {path, from, to}` / `{path, structural: true}` |
| `admin` `status` / `repo` | `index_status {}` |
| `admin` `rescan` | `index_rescan {paths?}`（`full` 移除；`{}` 就是整個 workspace） |
| `admin` `cache_stats` / `gc` / `cache_clear` / `telemetry` | CLI-only |
| `workspace` 全部 mode | CLI-only（`basemind workspace ...`）；`claim` / `release` 完全移除 |
| `agents` 全部 mode | `agent_post`、`agent_inbox`、`agent_threads`（agent comms v2，ADR-0021） |

同時移除的工具：`graph`、`web`、`shell`、`workspace`；`memory` 的 `audit` / `mine` / `proposals` / `accept` / `reject` 也移除。`code_refs` 承接 callers / implementations / importers / definition 的查詢。

**插件影響**：插件從 `tools/list` 動態註冊，不硬編碼工具名，因此不需要為 rename 改 runtime；但不能模擬舊工具，也不應把 CLI-only 功能補成工具。

### 2.2 參數重新命名與移除

- `path_contains` → `path`，且語意改為 prefix；值含 `*` 時視為 glob（`*` 不跨 `/`，`**` 跨）。
- `include_context` → `context`（0–10 的整數；預設關閉）。
- `line_start` / `line_end` → `line` / `end_line`；行號全部改為 **1-based inclusive**。
- `rev_old` / `rev_new` → `from` / `to`。
- `entity_category` → `entity`；`keywords_contains` → `keywords`；`tag` → `tags`（清單）。
- 移除 `mode`、`format`（`"toon"` 回應格式）、未公開 alias（`q`、`needle`、`token_budget` 等）、`field`、`full`、`ranges`。
- **未知參數改為拒絕**（以前會靜默丟棄），錯誤訊息會列出可接受的欄位。

### 2.3 結果格式與結構化結果

- 定位類工具（`code_symbols`、`code_grep`、`code_refs`、`find_files`、`git_log`、`git_diff`）改為「shell 會印出的 row」加必要欄位，不再每列重複 path / line / elapsed。
- `code_grep` 的文字區塊是行導向文字（`# <path>`、`## <symbol>`、`<line>: <text>`）；`code_outline`、`git_diff`、`find_files` 清單是 [TOON](https://toonformat.dev)；其他工具與 `find_files` + `min_lines` 仍是 compact JSON。
- `structuredContent` 與 CLI `--json` 對所有工具仍是 JSON，形狀如 `docs/UPGRADING.md` 的 Response fields / Lean rows。
- 錯誤是 **tool result**（`isError: true` + 文字 + `structuredContent: {"error", "retryable"}`），不是 JSON-RPC error；`error` 代碼為 `invalid_argument`、`unavailable`、`index_unavailable`、`busy`、`cancelled`、`internal`。
- 分頁語意：`next_cursor` 才代表還有下一頁；`truncated` 代表非使用者要求的截斷，`truncated_reason` 說明原因；`budgeted` 代表被 token budget 裁剪。

### 2.4 MCP capabilities、instructions、resources

本次 0.34.0 真實 `initialize` 回應（已確認）：

```json
{
  "protocolVersion": "2025-06-18",
  "serverInfo": { "name": "rmcp", "version": "3.11.0" },
  "capabilities": {
    "extensions": { "io.modelcontextprotocol/tasks": {} },
    "completions": {},
    "prompts": {},
    "resources": {},
    "tools": {}
  }
}
```

- `serverInfo.name` 是 `rmcp`，`version` 是 **rmcp 版本，不是 BaseMind 版本**；插件不得用它判斷功能（與 [AGENTS.md](../AGENTS.md) 既有規則一致）。
- server instructions 為 **2,627 bytes**（0.34.0），遠低於插件 32 KiB 上限。
- `resources/list`：`basemind://status`（JSON）＋ templates `basemind://outline/{path}`（`text/toon`）、`basemind://memory/{key}`（JSON）。
- `basemind://repo/map` 隨 `graph` 工具移除；README 目前仍提到它，必須更新。
- `resources/subscribe` 未實作；插件本來就沒有訂閱。
- `tools/list` 的 `annotations` 是精確的：除 `memory_save`、`index_rescan` 外都是 read-only；沒有 destructive tool。`_meta["anthropic/alwaysLoad"] = true` 只標在 verb tools，agent tools 保持 deferred。
- 插件目前忽略 `annotations` 與 `_meta`，也沒有把它們傳給 DSH；DSH 的註冊路徑不會因這兩個欄位而改變工具的可見性或審批。這不影響 0.34 的註冊與呼叫，但也不應據此把 `isConcurrencySafe()` 改成 true（見 §6）。
- `capabilities.prompts` 存在，但插件依既有政策不 bridge prompts；`capabilities.completions` 同理。

### 2.5 MCP Tasks（SEP-2663）

- 伺服器 capabilities 以 `extensions.io.modelcontextprotocol/tasks` 宣告；只有 **client 在 initialize 宣告支援** 時，`index_rescan`、`code_search`、`docs_search` 超過 3 秒才會變成 task handle（`src/mcp/tasks.rs` 的 `TASK_THRESHOLD`）。
- 0.34 的設計是「快呼叫 inline，慢呼叫才給 task」；client 不宣告就不會有 task。
- 插件 initialize 送 `capabilities: {}`，因此 0.34 一律 inline；本次採集所有呼叫（含 `index_rescan` 53 ms、`docs_search` 47 ms）都是 inline result。

### 2.6 CLI、daemon、repository group、worktree、view 與索引遷移

- `serve` 仍接受 `--root .`，新增 `--lead`（Unix only，插件不使用）；`--view working|staged|rev-<sha7>` 仍由使用者 args 決定（插件的 `stripRootArgs` 只剝奪 `--root`，其他 args 原樣傳遞）。
- 0.34 對 boolean `BASEMIND_*` 值的解析變嚴格：只接受 `1/true/yes/on` 或 `0/false/no/off`，空值視為未設定，其他值會讓每個命令失敗並指名變數；`BASEMIND_GRAMMAR_OFFLINE`、`BASEMIND_GIT_DISCOVER_PARENTS` 的 `false` 現在真的表示 false。`BASEMIND_ALLOW_EXTRA_ROOTS` / `BASEMIND_ALLOW_DEPENDENCY_ROOTS` 讀 path list；`BASEMIND_ALLOW_HTTP_REMOTE` 控制非 loopback HTTP。`BASEMIND_COMMS_DIR` 下的 socket / lock / log / store 多了一層 `g1/`。
- 插件不設定這些變數，只透過 `scrubEnv` 轉送使用者環境；若使用者在 DSH 環境設定非法 boolean，會看到 BaseMind 自己的錯誤，插件只如實回報（不在插件內修正或吞掉）。
- `RELEASE_MINOR 33 → 34`：每個 view（`working` / `staged` / `rev-<sha7>`）第一次以新 writer 開啟時重建索引；blob store 移到 `cache/blobs/v34/`；每個檔案重新 extract、每份 document / code chunk 重新 embed 一次。
- 一個 **repository group 一份索引**（ADR-0028），由所有 worktree / view 共用；memory notes 與 document store 也改為 group 範圍（0.30 起逐步遷移）。
- daemon 的 socket / lock / log / comms store 移到 `comms/g1/`，registry 移到 `daemons/g1/`；daemon protocol 4 → 7，relay protocol 1 → 2。
- 0.33 daemon 與 0.34 daemon **互不共用**；升級窗口內若舊 session 仍持有 repo index，新 session 的 `initialize` 最多等 10 秒，之後仍可連上並列出工具，但工具呼叫會得到 retryable 的 `backend_unavailable`（`-32003`），直到舊 daemon 放手（最後一個 client 關閉後 10 分鐘，或 `basemind comms stop`）。
- 升級步驟要求：`basemind comms stop`（換掉 0.33 daemon）→ `basemind scan`（重建索引）→ 重開每個 session。插件不應代做，但文件必須寫清楚。

### 2.7 0.29.3 → 0.33 之間與插件相關的變更

| 版本 | 變更 | 對插件 |
|---|---|---|
| 0.30.0 | index schema 升級；memory 移到 per-repo-group `memory.fjall`；文件 tier 調整 | 工具名稱 / schema 不變；插件無需修改 |
| 0.31.0 | index / git-history schema 升級；`grep_bloom` layout | 同上 |
| 0.31.1 | 依賴與 toolchain；無 schema 變更 | 同上 |
| 0.32.0 | Python 3.11 下限、依賴升級；無 MCP 表面變更 | 0.1.6 已實測於 0.32.0 |
| 0.33.0 | `BASEMIND_INDEX_LAYERED=1` 的 shared worktree index（opt-in）；blob / index / git-history / memory schema 升級；plugin resources 索引 | 工具名稱 / schema 不變；worktree 共用索引的語意從這裡開始，0.34 變成預設 group index |

**結論**：插件實際支援的舊版範圍可視為 **0.29.3–0.33.0**；其中 0.32.0 是上一個明確驗證版本。0.34.0 是第一次真正的 MCP 工具破壞性變更。

## 3. 現有插件相容性分析

### 3.1 動態 discovery 與註冊（已相容）

- [index.js](../index.js) 以 `session.listTools()` 的結果建立 `ToolDefinition`（`definitionsFor`、`syncTools`），不依版本字串分支，也不硬編碼工具名；因此 0.34 的 15 + 3 個工具可以直接註冊。

### 3.2 Schema 正規化（已相容，無降級）

以本次真實 `tools/list`（18 工具、24,767 bytes JSON）逐項比對：

- 全部通過 `normalizeInputSchema` 與 `validateJsonSchemaNode`；沒有任何 tool 被降級為 unconstrained object。
- 每個工具的 `properties` 名稱集合與 raw schema 完全相同；`required` 陣列完全相同；`enum` 值（`code_refs.relation`、`code_refs.match`、`code_search.lane`、`memory_*` 的 `visibility`）完全相同。
- 0.34 的 schema 只使用 `type`、`properties`、`required`、`items`、`enum`、`additionalProperties`、`description`；沒有 `$ref` / `$defs` / `anyOf` / `allOf` / `oneOf`，因此 [lib/schema.js](../lib/schema.js) 的降級路徑不會被觸發。
- 官方在 `tests/mcp_schema_wire.rs` 也把 `$ref`、`$defs`、`oneOf`、`anyOf`、`allOf` 列為禁止項，並有 20 KB 的 verb tools byte ceiling；這與本次採集一致。
- `code_read` 的 schema 只 required `path`，但 tool body 要求 `symbol` 或 `line`；這是上游 schema 與 body 的落差，不是 normalizer 問題。模型只給 `path` 時會收到可操作的 `isError`（本次採集已確認），插件不應改寫官方 schema。

### 3.3 結果投影（部分相容：structuredContent 丟失）

- [lib/mcp-session.js](../lib/mcp-session.js) 的 `callTool` 已經把 `structuredContent` 放進回傳物件（第 208 行）。
- [lib/tool-bridge.js](../lib/tool-bridge.js) 的 `execute` 只回傳：


  - 成功結果的結構化資料（例如 `code_grep.hits`、`index_status` 全部欄位、`code_refs` 的 grouped hits）在 DSH 端不可取得。

- 插件沒有把 0.34 的 `annotations`（`readOnlyHint` 等）轉成 DSH 的權限或併行 metadata；插件目前也沒有把這些欄位傳給 DSH。DSH 是否另有原生 annotation / 唯讀策略支援，本次沒有確認。因此：
  - 不會因為 annotation 而放寬任何審批；
  - 但也不會利用 `readOnlyHint` 做唯讀工具自動允許或並行（屬新功能，本次不納入）。

## 5. 必須修改的具體內容及依據

### 5.1 `lib/tool-bridge.js`：保留 structuredContent 與錯誤代碼

**問題**：0.34 的 `structuredContent` 是唯一的穩定 JSON 形式（尤其文字改 TOON 的四個工具），也是錯誤 `{error, retryable}` 的載體；目前被丟棄。

**改法（最小）**：

1. 在 `RESULT_SCHEMA.properties` 增加 optional `structuredContent`：

   ```js
   structuredContent: {
     description: 'MCP structuredContent for this result, when the server sends one.',
   },
   ```

   不要加入 `required`；舊 server（0.29.3）沒有這個欄位。

2. `execute` 成功時有條件帶上：

   ```js
   const value = {
     text: resultText(result),
     content: Array.isArray(result?.content) ? result.content : [],
     isError: false,
   }
   if (result?.structuredContent !== undefined) {
     value.structuredContent = result.structuredContent
   }
   return value
   ```

3. `isError` 時把代碼與 retryable 併入錯誤訊息（文字仍是 server 的原文，模型可讀）：

   ```js
   const failure = isPlainObject(result.structuredContent) ? result.structuredContent : undefined
   const code = typeof failure?.error === 'string' ? failure.error : undefined
   const retryable = failure?.retryable === true
   const suffix = code === undefined ? '' : ` [error=${code}${retryable ? ', retryable' : ''}]`
   ```

4. JSON-RPC error 的 `code`（例如 `-32602` 舊工具、`-32003` 升級窗口、`-32800` 取消）併入 wrapper 訊息，方便診斷；不改變 throw 的類型。

**依據**：

- 0.34 UPGRADING.md「Errors are tool results」「Errors carry a code」。
- 本次採集：`code_read` 缺失參數回 `isError: true` + `structuredContent: {error: "invalid_argument", retryable: false}`；`code_symbols` 未知參數同理。
- 本次 plugin probe：`code_grep` 的 envelope keys 只有 `text`、`content`、`isError`，`structuredContent` 不在其中。

**不在本次改動**：

- 不把 `structuredContent` 直接渲染給模型（會增加 token；文字已足夠）。
- 不重試 `isError`；保留「一次呼叫一次結果」的既有語意。
- 不改 `isConcurrencySafe()`（見 §6）。

### 8.5 慢查詢與 timeout

- fake server：`code_search` / `index_rescan` delay 大於 `toolCallTimeoutMs`，驗證：
  - plugin reject 的錯誤包含工具名與 root；
  - client 有送 `notifications/cancelled`；
  - 後續同一個 relay 還能呼叫（沒有被 timeout 弄壞）。
- 真實：在 0.34 的大型 repo（至少 10k 檔案）量測：
  - 第一次 `index_rescan {}` 耗時；
  - `code_search` cold/warm 耗時；
  - 120 s timeout 是否會誤傷正常操作。
- 決策：若量測顯示常態超過 120 s，**只更新文件與建議設定**（`toolCallTimeoutMs`），不擅自改預設；若使用者要求改預設，另案處理。

### 8.6 多 Session / 多 Repo / Worktree

- 測試 repo 建 `git worktree add -b probe-wt ../wt`。
- Session A（main）與 B（worktree）：
  - `index_status.root` 分別是 main / wt；
  - `code_outline` / `code_symbols` 在兩邊都成功；
  - `memory_save` 在 A、`memory_search` 在 B：0.34 會讀到（group 共用），測試只記錄這個行為，不把它當成隔離失敗；
  - 兩個 relay 的 process 不同，關閉 A 不影響 B。
- 不同 repo：各自 temp git repo，`index_status.root` 不互相污染；memory key 不跨 repo（除非同一 group）。
- 注意：Windows 路徑大小寫不敏感；pool 已用 `path.resolve` + lower-case key（[lib/workspace-pool.js](../lib/workspace-pool.js)）。

### 8.7 Windows / macOS

- Windows：本機 real binary；`.exe` 直接 spawn、不需 cmd wrapper；`serve --root .` 可用；`taskkill`/terminate 只殺自己的 tree。
- macOS：CI `compat.yml` 用 `basemind-aarch64-apple-darwin.tar.gz`（arm64 runner，例如 `macos-14`）；驗 initialize / tools/list / `index_status` / `code_outline`；不驗 DSH Desktop。
- 不在本次驗證：Windows 上的 `.cmd` npm launcher（若使用者用 npm 安裝 basemind）；既有 `executable.test.mjs` 已覆蓋 wrapper 邏輯，但 0.34 的 npm launcher 佈局未實測（列入 §11）。

### 8.8 DSH Desktop 驗收細節

- 使用獨立 test profile / `DSH_HOME`，不要動 `~/.dsh/profiles/desktop` 的 `dsh-basemind-plugin` 版本。
- 依 DSH 的 profile 規則安裝 local tarball；若用 web 測試實例，先清除 `DSH_WEB_URL` / `DSH_PROFILE_DIR` / `DSH_PROFILE` / `DSH_SESSION_ID` 再啟動（避免 `?token=` 401）。
- 驗收命令 / 操作：
  1. 開 session（工作目錄 = 測試 git repo）。
  2. 呼叫 `mcp__basemind__index_status`（空索引也應回 JSON / notice）。
  3. 呼叫 `mcp__basemind__code_grep`（TOON 文字）。
  4. 呼叫 `mcp__basemind__code_read` 只給 path（應得到可讀錯誤）。
  5. 讀 `basemind://status`。
  6. 停用插件，確認工具消失、無 relay 殘留。
- 標準 preset 不動；若 preset 的 prompt 仍寫舊工具名，只記錄，不在本次改 preset。

## 9. 版本相容性策略

- **不設版本閘門**：插件不解析 BaseMind 版本，也不以 `serverInfo.version` 分支；能力以 `tools/list`、`initialize.capabilities`、`resources/list` 為準。
- **支援矩陣**：
  - 0.29.3：fixture 回歸（已存在）。
  - 0.30–0.32：工具表面不變；0.32.0 曾實測。
  - 0.33.0：工具表面不變；worktree 共用索引為 opt-in；legacy smoke（可選真實 binary）。
  - 0.34.0：目標版本；15 verb + 3 agent tools；fixture + 真實 integration。
- **降級行為**：
  - 舊 server 沒有某個工具 → 不註冊；呼叫不存在的工具 → 清楚的 JSON-RPC 錯誤。
  - 舊 server 沒有 `structuredContent` → envelope 沒有該欄位，錯誤訊息格式不變。
  - 新 server 的未知工具 / 未知參數 → server 回錯誤；插件不自行補齊或改名。
- **混合 relay**：不同 root 可能由不同 BaseMind 版本服務（升級窗口）。插件以每個 relay 的 `hasTool` 把關（[lib/tool-bridge.js](../lib/tool-bridge.js) 第 116–120 行）；不做跨 relay 的工具集合合併。文件要求升級後重開 session。
- **DSH 版本**：`engines.dsh` 不變（`>=0.2.1-rc.3 <0.3.0-0`）；本次沒有使用新的 DSH API。
- **Node**：不變（`>=24.20.0`）；零新增依賴。

## 10. 發布與回滾方案

### 10.1 發布

1. 使用者人工審查 Phase 1–6 的 diff 與 Execution Report。
2. 使用者手動 commit（建議訊息：`feat: 適配 BaseMind 0.34.0 並發布 0.2.0`）。
3. 使用者手動 `git tag v0.2.0` 並 push tag；[release.yml](../.github/workflows/release.yml) 會：
   - 檢查 tag 與 `package.json` 版本一致；
   - 跑真正含 BaseMind 的 `npm test`（§5.9 的改動）；
   - `npm pack`、publish、建立 GitHub Release。
4. 發布後在 README / Release notes 明示：
   - 需要 BaseMind 0.34.0（或至少支援 0.29.3–0.34.0）；
   - 升級 BaseMind 時要 `basemind comms stop` + `basemind scan` + 重開 session；
   - 工具名稱已改變，舊的 `mcp__basemind__code` 等設定需更新。
5. 不執行 `npm run release`（它會 commit / push）；由使用者手動 tag。

### 10.2 回滾

- **插件回滾**：在 profile 安裝 `dsh-basemind-plugin@0.1.6` 即可；插件沒有資料遷移、沒有寫入使用者索引。
- **BaseMind 回滾**：
  - 0.34 的 index schema 34 / blob v34 / group index 是 upstream 格式；降回 0.33 會觸發 release-minor 重建，不是資料遺失，但需要時間與磁碟空間。
  - 0.34 的 memory notes 存在 group store；舊版是否可讀取決於 upstream，回滾前應先備份 `BASEMIND_DATA_HOME` 與 repo 的 `.basemind`（若存在）。
  - 不在本次計畫中執行任何降版或索引清理。
- **發布失敗**：若 npm publish 後發現問題，優先用 `0.2.1` 修復；不要刪 tag / 重寫 history（除非使用者明確授權）。

### 11.1 明確的未驗證範圍

- 沒有在 macOS / Linux 實機跑過 0.34.0 的 `basemind serve`；只有 Windows 真實採集。
- 沒有在 DSH Desktop 實際 session 中載入 0.2.0；只有 fake context + real binary 的端到端 probe。
- 沒有用 0.33 / 0.32 真實 binary 跑 integration；只有 0.29.3 fixture。
- 沒有用 10k+ 檔案的大型 repo 量測首次 rebuild / timeout。
- 沒有製造超過 3 秒的成功 `tools/call`；`index_rescan` / `code_search` 在大型 repo 的實際耗時與 timeout 後行為未量測。
- 沒有模擬新舊 daemon 同時持有同一 repo 的升級窗口。

### 11.2 風險排序

1. **高**：release 假通過（integration skip）→ 必須以 `BASEMIND_REQUIRE_INTEGRATION=1` + release gate 修正。
2. **高**：使用者可見工具名改變，既有設定 / prompt 失效 → 文件與 CHANGELOG 必須明示。
3. **中**：大型 repo 首次 rebuild timeout → 量測後決定文件或設定建議。
4. **中**：升級窗口 `-32003` 被誤判為插件故障 → 文件說明；錯誤訊息保留 code 有助診斷。
5. **低**：`structuredContent` 大小 / memory → optional 欄位，不渲染。
6. **低**：macOS / DSH Desktop 未驗證 → Phase 4/5 補齊。

## 結論

0.34.0 的破壞性變更主要落在 **BaseMind 的工具表面**，而本插件原本就把它當作動態資料，因此不需要重寫 bridge、也不需要版本閘門。最小充分方案是：

1. 補上 `structuredContent` 與錯誤代碼的保留；
2. 用真實 0.34 fixture + 更新後的 integration 測試把契約固定住；
3. 更新文件、版本與 release gate，讓舊版回歸與真實 0.34 都不得被 skip。

完成上述修改後，插件可在同一份程式碼上同時服務 0.29.3–0.34.0；0.34 的使用者會看到新的 verb tools 名稱，這是上游設計，應以文件與 CHANGELOG 說明，而不是在插件內模擬舊工具。
